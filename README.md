# NuProc Ontology

An OWL 2 ontology, SKOS vocabularies and SHACL shapes for **engagement events in nuclear new-build
procurement**: the meetings, visits, negotiations, signings and public commitments through which
parties engage over a procurement case, whether or not they were reported. The ontology keeps these
apart from the news reports, coded records and coding claims through which they are known.

- **Namespace** `https://w3id.org/nuproc/ns#` (registered at w3id.org; see *Status*)
- **Version** 0.9.0 · **Licence** CC BY 4.0 (the legal code is in `LICENSE`)
- The licence matrix (`LICENSES.md`) is in Korean; the modules carry Korean annotations beside the English
  ones, and each query file states its question in English before its Korean comments.

## What the ontology does

The ontology has a **real-world layer** (engagements, the organisations that take part in them and
their roles in a procurement case) and an **information layer** (the records, clusters, coded
participations, actor references and claims that report them). Each design decision was argued in a
design record (ADR) before it was implemented; the ontology cites these records by number, and they
are available on request (see *Design records*).

| Element | What it does |
|---|---|
| **Engagement vs report** | An `Engagement` is a process (BFO process) in which parties engage over a new-build procurement case. An `EventRecord` is one article's coded report; an `EngagementCluster` groups the records that share a six-element key under an explicit clustering rule. A cluster stands for an engagement without determining its identity; it states what its identification with one engagement rests on (the key alone, a person's check, or a person's finding that it merges engagements) and, separately, the reported occurrence status (*occurred*, *planned*, *denied*, *unclear*). Only an unmerged cluster recorded as *occurred* reports an engagement (ADR-0027, ADR-0040, ADR-0041). |
| **Roles in a case** | An `EngagementRole` (BFO role) is borne by one organisation in one procurement case and realized in the engagements of that case in which the organisation acts in that role, whether in several or in none that the data record. Two side roles (export, host) and six role facets (technology supply, construction contract, financing, state sponsorship, commercial supply, other) are pairwise disjoint, so one organisation can bear several roles, which one engagement may realize together. What an organisation *is* (its type) is kept apart from the roles it takes (ADR-0014, ADR-0040). |
| **References and their resolution** | A participant that does not resolve to a registered organisation is represented by its reference (definite organisation, candidate set, collective, anonymous singular or national side), with a resolution status its kind admits (*resolved* or *unresolved* for a definite reference, *unresolvable_candidate_set* for a candidate set, *unresolvable_collective* for the other three kinds). Each judgement of a reference is a claim (`ResolutionClaim`) with its activity, agent and plan, and the reference carries the values of its final claim. No organisation is invented. A group acting as one party, such as a consortium, is one organisation whose members `org:hasMember` names (ADR-0008, ADR-0031, ADR-0041, ADR-0043). |
| **Claim-level coding provenance** | Each asserted role value, occurrence status, reference resolution and cluster identification has exactly one final claim (`RoleClaim`, `OccurrenceClaim`, `ResolutionClaim`, `IdentificationClaim`), generated by a coding, clustering, adjudication or judging activity whose qualified association names its agent and its plan (codebook version, prompt specification, protocol or rule). Claims that were not adopted stay in the graph as non-final claims, and a claim can name the claim it revises (`prov:wasRevisionOf`; ADR-0033, ADR-0039, ADR-0040, ADR-0041, ADR-0043, ADR-0044). |

A facet role is asserted only from the final claims that support it, and only a cluster recorded as
*occurred* grounds a role. This is a rule about what counts as evidence when roles are asserted
from reports. A role can exist before any meeting (a contracted role, for example), but a report of
an engagement that is not stated to have taken place is not used as evidence for it.

The SHACL shapes come in two layers (ADR-0034): a **pattern** layer of 20 named shapes for any dataset
that uses the four patterns (two-sided participation, reference resolution, coding provenance and
the real-world layer), and a **profile** layer of 27 named shapes for the NuProc dataset and codebook.

## Using the release

The modules import one another by their w3id IRIs, which resolve to the files of this repository; to
work offline, load the files from `ontology/` directly. The examples below use Python with rdflib and pySHACL (checked with Python
3.14.3, rdflib 7.6.0 and pySHACL 0.40.1 on Windows 11); any SPARQL 1.1 engine and SHACL processor can
be used instead.

**Validate the synthetic graph.** The shapes read the controlled vocabularies and the class
hierarchy, so the three OWL and SKOS modules are merged into the data graph:

```python
from rdflib import Graph
from pyshacl import validate

data = Graph()
for f in ("kg/public/nuproc-demo.ttl", "ontology/nuproc-core.ttl",
          "ontology/nuproc-codebook.ttl", "ontology/nuproc-alignments.ttl"):
    data.parse(f)
shapes = Graph().parse("ontology/nuproc-shapes.ttl")
conforms, report, text = validate(data, shacl_graph=shapes, advanced=True, inference="none")
print(text)
```

The shapes report no violation and four warnings (`sh:Warning`, from channel regularities), so in
SHACL's terms the graph does not conform.

**Run the queries** on the same merged graph:

```python
from pathlib import Path

for d in ("queries/v0.9/competency", "queries/v0.9/demonstrations", "queries/examples"):
    for q in sorted(Path(d).glob("*.rq")):
        print(q.name, len(list(data.query(q.read_text(encoding="utf-8")))))
```

Twenty-seven of the 29 queries return rows on the synthetic graph; CQ10 and CQ13 return none. In
`queries/examples/`, G6 reads the roles of the organisation in Figure 1b of the report through both layers, and G7–G9 are the worked examples of the
supplementary material: a candidate set of an ambiguous reference is not a participant (G7), an asserted value is
traced to the claim it revised or was derived from (G8), and the role claim of a cluster whose engagement is
planned supports no role, while no planned, denied or unclear cluster reports an engagement (G9). The values are synthetic, so the rows are not results about the
cases; those are given in the report.

**Check the shapes** against their test graphs: `python tests/run_fixtures.py` validates each of the 112 graphs in
`tests/fixtures/` and compares the result with `tests/fixtures/EXPECTED.csv` (`tests/README.md`).

**Check the files** against `ontology/CHECKSUMS.txt`, which lists the SHA-256 of each module.

## Evaluation

The report gives these results. Coding protocols and codebooks were frozen and checksummed before
each coding, and scoring scripts before the human codings were read; the records are available on
request (see *Access*). Every expected result of the competency questions was derived after the
data had been seen, so this is a **post hoc comparison, not a preregistered evaluation**.

| Axis | Result on 0.9.0 |
|---|---|
| **A — Competency questions** | 18 answered fully · **2 partially** (CQ03, CQ11) · 0 failed, of 20 |
| **B — Formal quality** | HermiT (ROBOT 1.9.10) finds the modules consistent, alone and merged with the populated graph (104,706 triples in all), with no unsatisfiable named class, and each of the 100 intersections of a real-world class with a NuProc class outside the real-world layer unsatisfiable. The shapes report no violation on the design and demonstration graphs, with five and four warnings respectively from channel regularities; 15 conformant test graphs pass, and each of 97 built to break one rule fails only on the shapes declared for it |
| **Human validation** | Role facets: two coders on a stratified sample of 150 events agree at Krippendorff's α 0.836 (MASI distance); the model's weighted precision is lowest for technology supply (0.74), its recall for *other* (0.65). Occurrence status: two coders on another sample of 150 agree at Cohen's κ 0.703, and the model with their adjudicated reference at κ 0.869; no cluster was coded *denied* |
| **C — Related resources** | Twelve elements of NuProc 0.9.0 compared term by term with ten resources; each of the 189 quotations behind the comparison was found in its source |
| **E — Withheld case** | A fourth case, withheld from every design artefact except the frozen codebook and coded under the same role and occurrence protocols by the model alone, loads on 0.9.0 with all 184 events and no new term or violation; 158 of its clusters report an engagement, and 26 of its references are unresolved, a status absent from the design data. The source events of all four cases had been coded before ontology work began, and the case had been loaded on earlier versions before 0.9.0 was designed, so this is an **artefact-level re-application audit, not a blind transfer test** |
| **F — Regression** | 382 of 386 benchmark cells reproduced; the 4 that did not lie in two columns whose original definition the source data dictionary does not state. A further **6 items (5 tables and 1 column) lie outside that denominator**: the ontology has no term for what they report, so they are candidates for a later version rather than failures |
| **G — Graph-native** | 5 demonstration queries on the populated graph, all returning rows |
| **H — Other datasets** | On samples of the European Commission's register of meetings with interest representatives, POLECAT and the UCDP Georeferenced Event Dataset, no record within a pattern's scope violates that pattern of the 0.9.0 pattern layer, and only resolved references were tested; this was checked post hoc and is not evidence. The real-world layer has no targets in these graphs and was not tested by them |

**Partial outcomes are not counted as successes**, and the four unreproduced cells are reported as
*not verifiable* rather than as reproduction failures: the source dictionary does not define how
those two columns were computed.

There is **no axis D**: no expert panel evaluation was performed, and nothing here should be read as
implying one.

## Limitations

1. **The events come only from one provider's news.** Engagement that drew no coverage is absent, and
   whether an engagement took place is known only from the reports. A cluster key can merge two
   meetings or split one; two coders checked a sample of clusters and the first author the 79 key-based
   clusters whose engagement realized two or more facet roles of one organisation, and 890 of the 1,026
   remain identified by the key alone. Each cluster that reports an engagement yields its own engagement individual, so two
   clusters can stand for one engagement.
2. **The coding step is not reproducible.** The source events, the role facets and the occurrence
   status were coded, and the bundled actor labels resolved, by large language models whose runs cannot
   be reproduced; people checked them on samples, and the first author re-judged the bundled labels.
   From this release, the modules can be checked against their checksums, the shapes and queries run
   on the synthetic graph and the shapes checked against their test graphs; rebuilding the modules
   needs the analysis code (on request); neither
   the coding nor the record-level graph can be reproduced by others.
3. **The real-world layer is partial.** Only the 559 engagements whose actor resolved to an
   organisation have a participant, none on the host side. Of the 1,090 final role values, 630
   support a role individual, but only 40 of 130 for financing and 11 of 205 for state sponsorship,
   the rest mostly on national sides.
4. **The withheld case is an artefact-level hold-out, not a blind test** (see axis E above).
5. **The import closure is not in OWL 2 DL.** The three OWL modules add no OWL 2 DL profile violation; the
   closure's violations lie in PROV-O and SKOS. Statements about profile conformance are made about
   NuProc's modules, not about the closure.
6. **One modelling gap remains open.** Whether an event type reads as a gateway or as a transaction
   is recorded in a design record; the graph does not carry it.
7. **The grounds of a role are not represented.** A role exists because of its bearer's circumstances
   in the case, such as a bid, a contract or state backing; the news record engagements, not these
   instruments, so a role is identified by its bearer, case and kind, and two contracts of one kind in
   a case ground one role.

## How this was made

The source events, role facets and occurrence status were coded, and the bundled actor labels
resolved, by large language models, as described above. The detailed record of that use is kept with the development records, in Korean,
and is not part of the public release.

During the preparation of this work, the first author used Anthropic Claude Opus 5 and 5.5 to assist with
drafting and revising the text, editing and translation, and the preparation of the code, checks and
documentation of this project. The authors reviewed, verified and edited these outputs as needed and
take full responsibility for the content.
